# 《资治通鉴》历史地理时间轴设计

## 1. 项目目标

制作一个浏览器中的交互式历史地理可视化，用横向时间轴呈现《资治通鉴》覆盖的历史时期，并让时间、朝代/政权、历史地域和地图疆域保持联动。

用户选择某一年或拖动时间轴后，系统应同步显示：

- 当前历史年份、传统纪年和重要事件；
- 当时存在的主要朝代与政权；
- 各政权在中国及周边地区的大致控制范围；
- 地图上的历史地名及其现代地理参照；
- 选中地域所属的政权、地名沿革和说明；
- 当前疆域数据的来源、近似程度和争议提示。

项目最终应覆盖《资治通鉴》主要记载范围，约从公元前403年至公元959年。首轮实现可以先用关键年代验证交互，但架构和数据格式必须支持完整时间轴，不得把最终目标缩减为少数静态年份。

## 2. 已确认的范围与边界

### 2.1 时间范围

内部使用带符号的整数年份：公元前年份为负数，公元年份为正数；界面不显示公元0年，而显示“前403年”“公元1年”“959年”等历史友好的标签。

时间轴允许选择每一年。地图不为每一年重复存储一份完整数据，而是在政权、疆域或重要地名发生变化的年份建立历史快照，其他年份继承最近的有效状态。

### 2.2 地域范围

“地域”定义为主要历史地理单元、郡国/州府、重要城市、都城、关隘、战役地点及具有叙事价值的地名，不承诺覆盖每个村落或每个文本中出现的小地名。

地图以世界地图作为空间参照，默认视图聚焦中国及东亚，同时保留周边和全球关系。疆域表达的是历史时期的大致控制范围，不等同于现代国际边界或精确测量结果。

### 2.3 史实表达

政权之间可能存在并立、割据、羁縻、名义臣属和实际控制不一致等情况。数据模型必须允许同一时期存在多个政权，并允许疆域状态标记为直接控制、间接控制、争议范围或影响范围。

所有疆域多边形均须允许附带来源和置信说明。争议区域使用透明度、纹理或虚线表达，避免把近似历史推断呈现为确定国界。

## 3. 推荐产品形态

### 3.1 页面布局

页面采用深墨色背景、暖白文字、泥金结构线和朱红强调色，延续现有《资治通鉴》视觉素材的暗色体系。

1. 顶部标题区：项目标题、当前年份和传统纪年。
2. 时间轴区：全时期概览、可拖动游标、关键历史节点、播放/暂停和年份输入。
3. 地图区：世界底图、中国及东亚重点区域、政权疆域、历史地名和现代参照图层。
4. 信息区：当前年份的政权摘要、主要事件、都城和疆域说明。
5. 详情浮层：点击地域或政权后显示名称、归属、现代位置、状态、来源和备注。

### 3.2 时间交互

- 拖动游标时，年份、朝代标签、政权图例、疆域和地名同步更新。
- 点击关键节点可直接跳转至相应年份。
- 播放模式按年份推进；当地图状态不变时可适当加速，状态改变时保留短暂停顿。
- 支持精确输入年份，输入负数时转换为“前X年”显示。
- 时间轴可以在下方显示当年主要政权的并行条带，让朝代更替与地图变化形成直接对应。

### 3.3 地图交互

- 点击政权区域：高亮该政权及其相关地域，信息区显示政权信息。
- 点击历史地名：显示历史名称、别名、现代位置、当年归属和地名说明。
- 支持政权疆域、历史地名、现代地理参照、事件地点四类图层切换。
- 地图需有图例说明颜色、线型、透明度与控制关系的含义。
- 地图缩放和投影变化不应破坏文字标注的可读性。

## 4. 数据模型

首版使用本地结构化数据，不依赖后端服务。建议按照以下概念组织：

### 4.1 YearSnapshot

```text
year: number
displayLabel: string
eraName?: string
calendarNote?: string
eventIds: string[]
activePolityIds: string[]
boundaryVersionIds: string[]
```

### 4.2 Polity

```text
id: string
name: string
type: dynasty | kingdom | regime | tribal_polity | local_rule
startYear: number
endYear: number
capitalPlaceId?: string
color: string
description: string
sourceIds: string[]
```

### 4.3 Region / Place

```text
id: string
historicalName: string
aliases: string[]
modernName?: string
modernAdministrativeUnit?: string
longitude: number
latitude: number
geometry?: GeoJSON
validFrom?: number
validTo?: number
notes?: string
sourceIds: string[]
```

### 4.4 BoundaryState

```text
id: string
polityId: string
validFrom: number
validTo: number
geometry: GeoJSON
controlType: direct | indirect | disputed | influence
confidence: high | medium | low
sourceIds: string[]
notes?: string
```

### 4.5 SourceNote

```text
id: string
title: string
authorOrInstitution?: string
urlOrCitation?: string
scope: string
note: string
```

时间查询层负责把某个年份转换为有效的政权、地域和疆域状态；地图渲染层不直接理解复杂的历史继承规则，只消费已经解析好的当前状态。

## 5. 技术方案

建议采用 React + TypeScript 的前端结构，使用本地 JSON/GeoJSON 数据。地图投影优先采用 D3 地理投影与 SVG/Canvas 图层，以便离线运行并避免对在线地图密钥的依赖；若后续疆域数据量增大，再将静态底图和历史边界迁移到矢量瓦片。

建议拆分为以下模块：

- `timeline`：年份范围、刻度、游标、播放和关键节点；
- `chronology`：年份、年号、朝代和政权的查询；
- `map`：投影、底图、疆域、地名和图层交互；
- `history-data`：本地数据、时间快照和来源；
- `detail-panel`：当前年份、政权、地域和来源说明；
- `theme`：与现有暗色视觉规范对应的颜色、字体和图形规则。

核心状态只保留一个当前年份和一个可选的选中实体：

```text
AppState = {
  currentYear: number,
  selectedEntity?: { type: 'polity' | 'place' | 'event', id: string },
  visibleLayers: LayerName[],
  isPlaying: boolean
}
```

所有界面组件从同一份解析后的 `HistoricalState` 读取数据，避免时间轴、地图和信息面板各自维护不同的年份逻辑。

## 6. 分阶段实施

### 阶段一：交互骨架

- 建立网页入口和暗色视觉主题；
- 完成时间轴、年份选择、关键节点和播放控制；
- 使用少量已核对的关键年代验证状态联动。

### 阶段二：地图和政权

- 加入世界底图和中国/东亚重点视图；
- 加入主要政权及其时间有效期；
- 加入首批历史疆域 GeoJSON；
- 完成图例、图层切换和政权点击。

### 阶段三：地域与地名

- 加入历史城市、都城、州郡、关隘和事件地点；
- 完成历史地名到现代位置的详情面板；
- 处理别名、同名异地和名称随时间变化的情况。

### 阶段四：扩展完整时间轴

- 覆盖前403年至959年的时间轴；
- 补齐政权更替和关键疆域变化；
- 为每个数据条目附来源和置信度；
- 用边界变化年份、政权并立年份和跨纪年年份进行验证。

### 阶段五：验收与视觉完善

- 检查时间轴、地图和详情面板是否始终使用同一年份；
- 检查前403年、公元1年、三国时期、南北朝、唐代和五代等代表年份；
- 检查移动端和窄屏布局；
- 检查地名重叠、疆域透明度和争议区域表达；
- 补充说明文字，避免把近似疆域误解为精确边界。

## 7. 验收标准

项目达到以下条件才算完成首个完整版本：

1. 时间轴能够选择《资治通鉴》主要记载范围内的任意年份。
2. 选择年份后，当前年份、朝代、政权、疆域和地图地名同步更新。
3. 地图能显示主要政权的大致控制范围，并区分直接控制、间接控制和争议范围。
4. 点击主要地域后，能够看到当时地名、所属政权和现代位置参照。
5. 同一政权可以在多个年份正确显示，政权更替不会残留旧状态。
6. 年号、前后纪年和公元1年前后的显示没有公元0年错误。
7. 关键历史数据有来源或说明，疆域的近似程度对用户可见。
8. 页面视觉风格与现有《资治通鉴》暗色图示素材保持一致。
9. 地图、时间轴和信息面板在代表性年份上经过实际操作验证。

## 8. 当前不纳入首版的内容

- 不把每一个村落级地名全部数字化；
- 不承诺复原现代意义上的精确国界；
- 不在首版加入账号、云端编辑、多人协作或后台管理；
- 不依赖实时在线地图服务才能运行；
- 不把存在学术争议的疆域强行归并成唯一结论。

这些内容可以在基础时间轴、地图和数据结构稳定后继续扩展。
